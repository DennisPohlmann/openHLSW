# openHLSW - notes for Claude

Rust (egui/eframe) remake of HLSW: game server browser and RCON admin tool
(`openhlsw` GUI, `openhlsw-cli`). Code layout: README section Code. egui's
painting crates are patched copies in `vendor/` (see `vendor/README.md`).

Build and check: `cargo clippy --all-targets -- -D warnings`, `cargo test`,
`cargo build --release`.

Version in `Cargo.toml` and `Cargo.lock`; history in `CHANGELOG.md`.

Releases: Conventional Commits + semantic-release (`.releaserc.json`). CI
(`.github/workflows/build.yml`) checks and builds all packages on every
push to `main` and every pull request (workflow artifacts);
`feat`/`fix`/breaking commits on `main` make semantic-release set the
version (`tools/set-version.sh`), write `CHANGELOG.md`, commit
`chore(release): vX.Y.Z [skip ci]`, tag `vX.Y.Z` and publish the GitHub
release, to which the packages built from that tag are added. There is no
tag-triggered workflow. Dependabot (`.github/dependabot.yml`) suggests
crate and GitHub Actions updates; egui updates stay manual.

## Security is part of every change (mandatory)

1. **Every change:** before you call a change done, commit it or open a PR,
   run the `security-check` skill on the diff and fix what it finds. Say in
   your answer which checklist points the change touched and the result
   (one or two lines are enough when nothing was found).
2. **Every release, without exception (standing rule from Dennis):**
   releases are made by semantic-release in CI when `feat`, `fix` or
   breaking-change commits reach `main` (version bump, `CHANGELOG.md`, tag
   `vX.Y.Z`, GitHub release). Before pushing such commits to `main`, run
   the `release-security-gate` skill over the whole repo, without asking
   first. Never tag by hand or edit version fields / `CHANGELOG.md`; report
   the gate result and ask Dennis for the go before the push.
3. **Sensitive data, every task (standing rule from Dennis):** before you
   call a task done, commit or publish anything, run the
   `security-privacy-audit` skill (credentials, personal data, IPs and
   hostnames, Steam IDs and other account identifiers, private files) over
   the working tree, the diff, docs and the commit message, and end the
   answer with its audit summary. A `BLOCKED` finding stops the commit;
   report only category and location, never the value.
4. A finding you cannot fix in scope goes into the answer with file:line,
   impact and a proposed fix. Never silence a check or weaken a validation
   to get green.

## Before every commit (mandatory, standing rule from Dennis)

Run the `pre-commit-checklist` skill before every `git commit`, together
with `security-check` and `security-privacy-audit`, also for small fixes:

1. Check `README.md` (and `vendor/README.md`, translations) against the
   change and update them in the same commit.
2. Write the commit message as a Conventional Commit (`feat:`, `fix:`,
   `docs:`, ... see the `pre-commit-checklist` skill). `CHANGELOG.md` and
   the version fields are generated by semantic-release; never edit them.
3. Check dependencies and toolchain for updates and *suggest* available
   updates (do not update on your own).
4. Check the licenses of third-party code and keep the license notes
   (README section License, **? → License** in the program) complete and
   current.
5. Run the `security-privacy-audit` skill on the staged changes and the
   commit message; do not commit while a check is `BLOCKED`.

Report the result of each step in one line in your answer and end with
the audit summary of `security-privacy-audit`.

## Mandatory Security and Privacy Policy

These rules apply to every task performed in this repository.

### Mandatory Security Audit

Before completing any task, review all changes for sensitive information. This includes source code, configuration files, README files, changelogs, commit messages, documentation, comments, logs, tests and fixtures, generated files, Git diffs and staged changes, release notes, and build artifacts.

### Never Expose Sensitive Information

Never introduce or publish real:

- Passwords, API keys, tokens, credentials, private keys, or authentication material
- Personal information, private files, or local configuration
- Sensitive IP addresses or internal infrastructure details
- Steam IDs and private account identifiers
- User IDs, device IDs, or private resource identifiers
- Database credentials or connection strings containing secrets
- Private URLs, logs, screenshots, or debug output

Do not copy sensitive information from existing files into new files. Use fictional placeholders in documentation and examples.

### Required Workflow

Before declaring any task complete:

1. Inspect the complete working tree.
2. Review all staged and unstaged changes.
3. Scan for secrets using available security tools.
4. Check personal information, identifiers, IP addresses, and private files.
5. Review README, CHANGELOG, documentation, and commit messages.
6. Fix findings introduced by the current changes.
7. Run relevant checks again.
8. Report the results honestly.

Never claim a security check passed unless it was actually performed.

### Blocking Rule

If an unresolved high-risk exposure exists, do not create the affected commit or publish the affected release. Do not print discovered secrets in terminal output or reports. Report findings using their category and file location without reproducing the sensitive value.

If a check cannot be performed, explicitly report that limitation.

### Mandatory Skill

Use the `security-privacy-audit` skill for repository changes. The security audit is part of completing every task, not an optional step.

Never trade security or privacy for convenience.
